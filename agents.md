# AGENCY WORKFLOW & COOPERATION PROTOCOL

> Проект: «Реквием: Последний выстрел» (The Wicked City)

---

## 1. Роли и зоны ответственности

### Руководитель проекта (User / Оператор)

- Определяет продуктовые приоритеты и утверждает задачи.
- Передаёт задачи кодеру и запускает команды в консоли (`node patcher.cjs; npm test`).
- Является финальной инстанцией: только пользователь решает, применять патч или отправлять на доработку.

### Технический архитектор (Gemini / AI Architect)

- Анализирует кодовую базу, архитектурные связи и риски регрессий.
- Перед генерацией ТЗ всегда формирует и выгружает актуальный контекст единой строкой PowerShell в `context.txt`.
- Формирует строгие, компактные и проверяемые технические задания для кодера.
- Проверяет предложенные патчи на безопасность, валидность JSON и логику.
- При одобрении патча выдает вердикт ПРИНЯТЬ без повторного листинга кода (только подтверждение соответствия и команда запуска тестов).
- Ведёт актуальный реестр кластеров и задач (чек-лист проекта).
- Обеспечивает инвариант Zero Regression: ни один шаг не принимается без зелёных тестов в Vitest (132/132).
- Не пишет код напрямую в рабочие файлы, а координирует архитектуру.

### ИИ-кодер (Coder)

- Реализует конкретное техническое задание строго в рамках указанных файлов.
- Создаёт компактный `patch.json` строго в формате точечных замен `find` -> `replace`. Дампы файлов целиком категорически запрещены.
- Не производит несанкционированный рефакторинг сторонних модулей.
- Строжайше соблюдает утверждённую палитру проекта. Самовольное использование цветов amber, yellow, cyan и ярко-зеленых запрещено навсегда.
- Гарантирует сохранение 100% работоспособности тестов Vitest (Zero Regression: 132/132).

## 2. Формат патчей (patch.json)

### Строгий запрет

Запрещено вставлять код файлов целиком (дампы на десятки тысяч символов) в строковые поля JSON. Это приводит к синтаксическим ошибкам экранирования и зависаниям редактора.

### Основной формат: Точечные правки (`patches`)

Для изменения существующих файлов используется массив замен `find` $\to$ `replace`:

```json
{
  "patches": [
    {
      "file": "src/components/Example.tsx",
      "find": "строка или блок для поиска",
      "replace": "строка или блок на замену"
    }
  ]
}
```

### Дополнительный формат: Новые файлы (`files`)

Используется только при создании нового изолированного компонента или модуля:

```json
{
  "files": {
    "src/components/NewComponent.tsx": "код нового файла"
  },
  "patches": [
    {
      "file": "src/App.tsx",
      "find": "import { Old } from './Old';",
      "replace": "import { Old } from './Old';\nimport { NewComponent } from './components/NewComponent';"
    }
  ]
}
```

## 3. Скрипт применения (`patcher.cjs`)

`patcher.cjs` размещён в корне проекта и поддерживает оба формата одновременно:

1. Создание/перезапись файлов из секции `files`.
2. Поиск и точечную замену фрагментов из секции `patches` с контролем наличия исходного текста.

---

## 4. Стандартный рабочий цикл (Pipeline)

1. **Постановка задачи:** Архитектор формулирует изолированную задачу и готовит промпт для кодера.
2. **Генерация патча:** Кодер формирует компактный `patch.json`.
3. **Аудит патча:** Архитектор верифицирует изменения (ПРИНЯТЬ / ДОРАБОТАТЬ / ОТКЛОНИТЬ).
4. **Применение и тесты:** Пользователь копирует манифест в `patch.json` и выполняет:
   ```powershell
   node patcher.cjs; npm test
   ```
5. **Фиксация статуса:** При зелёных тестах задача отмечается закрытой в чек-листе проекта, и команда переходит к следующей.

## 5. Важные правила

1. **Цветовая палитра:** Строжайший запрет на самовольное изменение согласованной цветовой палитры. Любые цвета amber, yellow, cyan и ярко-зеленые категорически запрещены во всем проекте. Допустимы только zinc (монохром), neutral, white, black, red (убийства/угроза/криминал), blue (детектив/закон). Менять или добавлять другие цвета разрешено ТОЛЬКО по прямому указанию пользователя.
2. **Регламент сдачи патчей:** Патчи формируются исключительно через точечные замены patches: [{ file, find, replace }]. Кодер никогда не выгружает файлы целиком в files, если файл уже существует в репозитории.
3. **Регламент утверждения:** Архитектор подтверждает решение вердиктом ПРИНЯТЬ, не дублируя код патча, и выдаёт команду node patcher.cjs; npm test для фиксации стабильности.
