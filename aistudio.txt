1. Карта архитектуры проекта

Проект представляет собой SPA на React 18 + TypeScript + Vite, использующее
Firebase Realtime Database (RTDB) в качестве бэкенда. Серверная логика (Cloud
Functions) отсутствует, игра работает по принципу Client-Driven / Host-Authority
(авторитетным является клиент Хоста).

Поток данных (Data Flow):

1.  UI (React): Компоненты (GameBoard, ActionPanel) вызывают локальные
    обработчики в App.tsx.
2.  Локальный State: App.tsx вызывает dispatchAction, который синхронно
    обновляет локальный gameState через чистую функцию gameReducer.
3.  Сеть (Firebase): Если действие локальное, оно передаётся в
    mpService.sendAction, сериализуется в JSON и пушится в узел
    rooms/$roomCode/actions.
4.  Удалённый клиент: mpService слушает onChildAdded в узле actions. При
    получении чужого действия оно десериализуется и отправляется в gameReducer.
5.  Синхронизация: Хост периодически (или при старте) сохраняет полный слепок
    состояния в rooms/$roomCode/gameState для восстановления сессии (F5).

2. Файлы, связанные с мультиплеером

  - src/utils/multiplayerPeer.ts — Ядро сети. Класс-синглтон MultiplayerService.
    Управляет анонимной авторизацией, созданием/поиском комнат, подписками на
    actions, presence (онлайн-статус) и восстановлением сессии.
  - src/utils/gameReducer.ts — Сетевой редьюсер. Применяет GameAction к
    GameState. Содержит критическую логику доверия удалённым действиям
    (например, принудительная установка currentTurn и activeSpyIndex из payload
    удалённого действия).
  - src/types/multiplayer.ts — Типизация сетевых действий (GameAction,
    BaseGameAction).
  - src/App.tsx — Главный контроллер. Связывает mpService и gameReducer.
    Управляет подписками, таймерами АФК, восстановлением сессии из
    sessionStorage и проигрыванием звуков на основе удалённых действий.
  - src/components/MainMenu.tsx — UI лобби. Создание комнат, Quick Play,
    подключение по коду.
  - src/components/MultiplayerLobbyModal.tsx — Модальное окно ожидания
    подключения.
  - src/components/RoleRevealModal.tsx — Фаза интро. Содержит логику
    синхронизации готовности (PLAYER_READY) перед началом матча.
  - database.rules.json — Правила безопасности Firebase RTDB.

3. Анализ мультиплеера: Факты и Гипотезы

✅ Подтверждённые факты (на основе кода)

1.  Оптимистичный UI: Клиент применяет свои действия мгновенно, не дожидаясь
    подтверждения от сервера.
2.  Защита от дублей: В multiplayerPeer.ts используется processedActionIds
    (хранит до 100 ID), чтобы не применять одно и то же действие дважды.
3.  Авторитет Хоста: При старте матча (MATCH_STARTED) и рестарте (RESTART_GAME)
    гость полностью перезаписывает свой локальный стейт стейтом хоста.
4.  Восстановление сессии: При перезагрузке страницы (F5) App.tsx читает
    sessionStorage, вызывает restoreSession, который забирает gameState из
    Firebase.
5.  Анти-отмена (Anti-undo): В gameReducer.ts блокировка обратного сдвига поля
    работает только для локальных действий. Удалённые действия применяются
    безусловно, чтобы избежать рассинхронизации, если хост уже засчитал сдвиг.
6.  Уязвимость лобби: Как указано в zesponse.txt, subscribeToPublicRooms
    использует onValue на весь узел public_rooms, что приведёт к
    экспоненциальному росту трафика при увеличении онлайна.
7.  Отсутствие валидации payload: database.rules.json не проверяет содержимое
    actionJson.

⚠️ Гипотезы и Риски (требуют внимания при патчах)

1.  Гонка состояний (Race Condition): Поскольку оба клиента применяют действия
    оптимистично, если Хост и Гость сделают ход одновременно (с разницей в
    миллисекунды), их локальные состояния разойдутся. В коде нет механизма
    отката (rollback) локальных действий при получении конфликтующего удалённого
    действия. Редьюсер просто применит чужое действие поверх своего.
2.  Рассинхронизация звуков: Звуки для удалённых действий проигрываются в
    App.tsx строго в момент получения пакета. При нестабильном интернете звук
    выстрела или сдвига прозвучит с задержкой, оторванной от реального времени
    хода.
3.  Утечка памяти в лобби: Если игрок быстро переключается между вкладками меню,
    подписки на public_rooms могут наслаиваться, если unsubscribe не
    отрабатывает корректно (хотя в useEffect очистка предусмотрена, стоит быть
    осторожным).
4.  Слепые зоны редьюсера: В gameReducer.ts удалённые действия применяются через
    computeNextState(). Если злоумышленник пришлёт KILL_CHARACTER не в свой ход,
    редьюсер его обработает, так как проверка isHumanTurn находится на уровне UI
    (App.tsx), а не в самом редьюсере.

4. Доступные проверки (Тесты и Инструменты)

В проекте настроена хорошая тестовая база на Vitest, которая покрывает
критические узлы:

  - npm run test — запуск всех тестов.
  - src/utils/networkReducer.test.ts — проверяет сетевую синхронизацию
    (переопределение currentTurn, игнорирование локального anti-undo при
    удалённом сдвиге).
  - src/utils/multiplayerFlow.test.tsx — интеграционные тесты сети (гонка
    PLAYER_READY, принятие стейта хоста, АФК-таймер).
  - src/utils/clusterAudit.test.ts — сквозной аудит инвариантов (маскировка,
    добор карт, авторитет хоста).
  - src/utils/comprehensiveRules.test.ts — математическая строгость поля 5x5 и
    проверка правил всех режимов.
  - npm run build (или audit:all) — строгая проверка TypeScript (tsc --noEmit) и
    сборка Vite.
